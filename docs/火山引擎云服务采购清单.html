🔬 七、高并发架构优化 · 理论基础与工程映射
1. Little's Law（利特尔定律）
Little, J.D.C. (1961). "A Proof for the Queuing Formula: L = λW". Operations Research, 9(3), 383-387.
L = λ × W
系统中平均排队数(L) = 平均到达率(λ) × 平均逗留时间(W)。这是排队论中最基础的不变量关系，适用于任何稳态排队系统。
工程映射：视频生成场景 λ=3500 任务/批次，平均生成时间 W=180s。需要同时在系统中驻留 L = (3500/600s) × 180s ≈ 1050 个并发任务。这直接决定了信号量池（Semaphore Pool）的容量设计——提交信号量 15 + 轮询信号量 50 + PollManager 无限容量的三层分离架构正是基于此推导。
2. Amdahl's Law（阿姆达尔定律）
Amdahl, G.M. (1967). "Validity of the Single Processor Approach to Achieving Large Scale Computing Capabilities". AFIPS Conference Proceedings, 30, 483-485.
S(N) = 1 / ( (1-P) + P/N )
加速比 S(N) 受限于串行部分比例(1-P)。即使 N→∞，加速比上限为 1/(1-P)。这是并行计算的基本约束。
工程映射：NanoStory 工作流中串行部分包括：剧本解析(<2s)、分镜文案生成(<5s)、最终视频合成(<3s)，约占总流程 <5%（P>0.95）。因此理论最大加速比 S = 1/0.05 = 20x。当前 2 台 ECS × 4 Worker = 8 路并行，远未触及天花板，扩容具有线性收益。
3. Fork-Join 并行与 Work-Stealing 调度
Blumofe, R.D. & Leiserson, C.E. (1999). "Scheduling Multithreaded Computations by Work Stealing". Journal of the ACM, 46(5), 720-748.
Tp ≤ T1/P + O(T∞)
Work-Stealing 算法中，P 个处理器的执行时间上界为：总工作量/处理器数 + 关键路径长度。空闲处理器从忙碌处理器的双端队列(deque)尾部偷取任务，实现动态负载均衡。
工程映射：NanoStory 的工作流引擎 WorkflowExecutor 采用 DAG 依赖图并行调度，本质是 Fork-Join 模型。已实现的 Round-Robin 公平调度是 Work-Stealing 的简化版 —— 当某用户任务提前完成释放槽位时，其他用户的排队任务可立即获得执行机会，避免资源空闲。
4. M/M/c 排队模型与 Erlang-C 公式
Erlang, A.K. (1917). "Solution of Some Problems in the Theory of Probabilities of Significance in Automatic Telephone Exchanges". Elektroteknikeren, 13.
P(wait) = C(c, λ/μ) = [(ρc/c!) × c/(c-λ/μ)] / [∑k=0c-1 (ρk/k!) + (ρc/c!) × c/(c-λ/μ)]
M/M/c 模型描述 c 个并行服务器的排队系统。Erlang-C 给出请求需要排队等待的概率。当负载因子 ρ = λ/(cμ) 接近 1 时，等待概率急剧上升。
工程映射：AI API 的 QPS 限制本质就是 c 个服务器。Seedance 默认 QPS=3 时 ρ=3500/(3×0.33)≈3535，远超 1（系统过载）。提升至 QPS=20 后 ρ=3500/(20×0.33)≈530，仍需排队但可在 10 分钟内清空。这是向火山引擎申请 QPS 提升的数学依据。
5. Pipeline Parallelism（流水线并行）
Hennessy, J.L. & Patterson, D.A. (2017). "Computer Architecture: A Quantitative Approach" (6th ed.). Morgan Kaufmann. Chapter 3: Instruction-Level Parallelism.
Throughput = 1 / max(Stage1, Stage2, ..., Stagek)
流水线将任务分解为 k 个阶段，不同任务的不同阶段可以重叠执行。吞吐量取决于最慢阶段（瓶颈阶段），而非所有阶段之和。
工程映射：漫剧生成流水线：文案生成(5s) → 图片生成(15s) → 视频生成(180s)。当分镜 #1 进入视频阶段时，分镜 #2 可同时进行图片生成，分镜 #3 做文案生成。信号量拆分（提交 vs 轮询分离）正是实现流水线重叠的关键——提交完立即释放槽位给下一个分镜的提交阶段。
6. Bulk Synchronous Parallel（BSP 整体同步并行）
Valiant, L.G. (1990). "A Bridging Model for Parallel Computation". Communications of the ACM, 33(8), 103-111.
Cost = max(wi) + h × g + l
BSP 将并行计算组织为"超步"（Superstep）：每个超步内各处理器独立计算，超步结束时进行一次全局同步（Barrier）。总开销 = 最大局部计算量 + 通信量×带宽倒数 + 同步延迟。
工程映射：NanoStory 的 PollManager 统一调度器就是 BSP 的工程实现——每 1 秒一个"超步"(tick)，在 tick 内批量检查所有到期轮询任务的状态（局部计算），然后统一发出查询请求（通信），等待下一个 tick（同步屏障）。相比每个任务独立 setTimeout，BSP 模式减少了 92% 的 HTTP 请求和定时器开销。
7. Optimistic Concurrency Control（乐观并发控制）
Kung, H.T. & Robinson, J.T. (1981). "On Optimistic Methods for Concurrency Control". ACM Transactions on Database Systems, 6(2), 213-226.
乐观并发控制假设冲突概率低，允许事务不加锁地并发执行，仅在提交时验证是否冲突。相比悲观锁（Pessimistic Locking），在低冲突场景下吞吐量显著提升。
工程映射：NanoStory 的信号量拆分策略本质就是乐观并发——提交阶段不持有长期锁（提交完立即释放），轮询阶段使用独立信号量池。这消除了"提交等待轮询完成"的锁竞争，使有效并发从 3 提升到 50+。数据库层面，计费记录采用 INSERT + 异步 UPDATE 而非 SELECT FOR UPDATE，同样是乐观策略。
8. Reactive Streams 与背压机制
Bainomugisha, E. et al. (2013). "A Survey on Reactive Programming". ACM Computing Surveys, 45(4), Article 52.
Reactive Streams 规范定义了异步流处理中的背压（Backpressure）机制：下游消费者通过 request(n) 信号告知上游自己的处理能力，上游据此调节发送速率，避免缓冲区溢出。
工程映射：NanoStory 的 Webhook 回调机制是 Push-based Reactive 模式的实现——AI 服务完成后主动推送结果（而非轮询拉取），消除了 3500 × 24 = 84000 次无效轮询请求。当 Webhook 不可用时降级为 PollManager 的 Pull 模式，形成 Push/Pull 混合的弹性策略。

▶ 已评估但不推荐采购的服务（实际收益不足）

  • Web 应用防火墙 WAF — 对 AI prompt 注入识别能力有限，已通过代码层参数校验 + JSON Schema + 黑名单词库实现更精准的防护。
  • 消息队列 RocketMQ / Kafka — Redis Bull 队列（8 分片 + 优先级调度）已足够，MQ 增加运维复杂度但并发提升有限。
  • 容器服务 VKE (K8s) — PM2 + 多 Worker + 弹性伸缩 AS 已满足需求，K8s 编排收益在当前规模下不显著。
  • Serverless 函数服务 — 工作流引擎需长时间运行（视频生成 3~10 分钟），与 Serverless 短执行时间模型不匹配。
  • 全站加速 DCDN — 用户和服务器均在国内，API 动态加速收益微小。
